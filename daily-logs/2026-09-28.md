## Notes

- Reasons why past predictive methods failed:
- **Initial three-step predictor:** Predictions took too long, frequently timed out, and became stale before execution.

- **Concurrent background prediction:** Added a second LLM request; fast tools finished before predictions, while unfinished requests still consumed compute and tokens.

- **Optional single-call lookahead:** DeepSeek usually omitted the optional prediction, so prediction was rarely used despite increased prompt complexity.

- **Mandatory one-step prediction:** Produced too few accepted predictions to yield a significant latency reduction; mandatory output also increased generation overhead.

- **Required fields and discrete confidence:** More complex schemas slowed responses, and a runaway task caused extreme latency before execution limits were added.

- **Selective coverage prediction before repairs:** The `polygon` keyword incorrectly triggered coverage mode, and the loose schema produced actions with missing arguments. All predictions were rejected.

- **Selective coverage prediction after repairs:** Predictions became valid, but only two were accepted. The coverage-only gate was too narrow, and the safety allowlist rejected one usable transition.

- **Always-mandatory prediction with limits:** Forced predictions even when new observations were necessary, increasing overhead. Difficult tasks then exhausted the wall-clock or LLM-call limits.

- **Overall problem:** Predictions were either too expensive, too infrequent, invalid, or launched where the next action was uncertain. The method rarely eliminated enough normal LLM calls to offset its own overhead.
- Reasons predictions not being used frequently for each method:
- **Initial three-step predictor:** Predictions usually timed out before Agent4Drone needed the next action. Multi-step predictions also became stale when an earlier action produced an unexpected result.

- **Concurrent background prediction:** Most simulator tools finished faster than DeepSeek could generate a prediction. Normal planning won the race, so the late prediction was discarded.

- **Optional single-call lookahead:** Prediction was optional in the response schema, and DeepSeek usually chose the simpler response containing only the current action.

- **Mandatory one-step prediction:** Predictions were proposed more often, but many were rejected for low confidence, missing information, invalid arguments, or dependence on the current action’s result.

- **Required fields and discrete confidence:** The schema forced prediction fields to appear, but appearing was not the same as producing a usable action. DeepSeek often returned low confidence or an empty prediction when uncertain.

- **Adaptive same-response prediction:** The model was explicitly allowed to skip uncertain predictions. DeepSeek interpreted many transitions as uncertain and therefore rarely populated the prediction.

- **Selective coverage prediction before schema repair:** Prediction was requested only at detected coverage transitions. Even then, malformed current actions and missing arguments prevented the associated predictions from being used.

- **Selective coverage prediction after schema repair:** The gate became too narrow. Only two transitions triggered selective prediction, optional prediction remained uncommon elsewhere, and the safety allowlist rejected one otherwise usable coverage transition.

- **Always-mandatory prediction with limits:** Predictions were always generated, but many could not be safely executed because the next action required a fresh sensing, movement, or failure result. Execution limits also ended some tasks before predictions could provide savings.
- Methods typically had an allowlist, a hardcoded validation rule consisting of a list of predicted actions permitted for automatic execution
- The memory baseline contains a requirement extractor, which parses designations like "Target 3" but not natural language like "the red car"
